# v21.7 New Game and Single-Player Practice Sets — Design

Date: 2026-08-22
Branch: `v21.7-new-game`
Base: `v21.6-known-good`

## Purpose

v21.7 will replace the current Play mode dropdown and separate multiplayer setup dialogs with a common game-starting experience that can support future game types and options without another UI redesign.

The release will also make the v21.6 element sets available to Single Player, so a player can practise First 20, First 36, All 118, or any chemical category using the normal single-player learning tools.

## Top-level navigation

The main toolbar will have two prominent actions:

- **New Game** — starts a new Single Player, Local 2 Player, or Online 2 Player host game.
- **Join Game** — joins an existing online game using a player name and room code or an invite link.

The existing **Play mode** dropdown in the burger menu will be removed. Game mode changes will only happen through New Game or Join Game, avoiding two competing ways to switch modes.

The existing burger menu remains for display and learning preferences such as sorting, colours, atomic numbers, tooltips, legend, help bar, action-button display, and settings JSON.

## New Game dialog

New Game is one shared setup dialog. It is divided into three logical sections.

### 1. Play mode

Selectable choices:

- Single Player
- Local 2 Player
- Online 2 Player

Changing the selected mode updates only the player/connection section. The common game settings remain the same.

### 2. Game settings

These settings apply to every play mode:

- **Game type**
  - v21.7 contains one game type: **Place Elements on Table**.
  - The control is intentionally designed as a selectable game-type field so later releases can add timed play, names-to-symbols, symbols-to-positions, atomic-number questions, weak-elements practice, and other formats without replacing the setup dialog.
- **Elements**
  - First 20
  - First 36
  - All 118
  - Alkali metals
  - Alkaline earth metals
  - Transition metals
  - Post-transition metals
  - Metalloids
  - Reactive non-metals
  - Halogens
  - Noble gases
  - Lanthanides
  - Actinides
- **Difficulty**
  - Beginner
  - Intermediate
  - Advanced
  - Custom

The Elements selector must use the existing shared `PeriodicElementSets` definitions rather than duplicate category membership in the UI code.

### 3. Players / connection

This section changes with the selected play mode.

#### Single Player

No additional player information is required in v21.7.

The primary action is **Start Game**.

#### Local 2 Player

Show:

- Player 1 name
- Player 2 name

The primary action is **Start Game**.

Existing local scoring and turn behaviour remain unchanged.

#### Online 2 Player

New Game is always the host/create path. Show:

- Host/player name

The common Game settings above are the settings stored for the room.

The primary action is **Create Room**.

Room code, invite link, presence, reconnect grace, scoring, rematch, expiry, and current Firebase validation behaviour remain unchanged unless a compatibility change is strictly required by the new UI.

## Join Game dialog

Join Game is separate from New Game so a guest is not presented with host-only settings.

Show:

- Player name
- Room code

Invite links should open the Join Game flow with the room code already filled where possible.

The guest cannot edit game type, element set, or difficulty. Those are host-owned settings.

Once room information is available, the dialog or joining status should display the host's chosen settings clearly before or while the guest joins.

The primary action is **Join Game**.

## Starting a new game while another game is active

Opening New Game must not immediately destroy the current game. The current board/session remains intact if the dialog is cancelled.

Only when the user confirms **Start Game** or **Create Room** does the application abandon/reset the current game and initialise the new one.

For an active online room, starting another game must run the existing leave/cleanup path before entering or creating the replacement session.

## Single Player element sets

Single Player gains the same shared element-set choices already used by multiplayer.

When a single-player game starts:

- The full periodic-table structure remains visible.
- Only elements in the selected set appear in the draggable element pool.
- Table positions outside the selected set remain visible but inactive for placement.
- Check Answers, Hint, Show Answers, Reset, sorting, colours, atomic-number display, and tooltips continue to work on the selected practice set.
- Completion/score counts use the selected set size, not 118.
- Reset restarts the current selected set rather than silently returning to All 118.
- All 118 remains the default single-player set for backwards compatibility.

Difficulty remains independent of element selection. For example, Noble gases can be practised in Beginner, Intermediate, Advanced, or Custom mode.

## Shared game configuration model

The UI should create one normalised game setup object before dispatching to a mode-specific starter. Conceptually it contains:

- play mode
- game type
- element set ID
- difficulty
- player information required by the selected mode

The common settings should not be separately re-read from three different dialogs. Single, Local, and Online start paths should consume the same normalised common settings, then add only mode-specific behaviour.

This is the extension point for later timed modes and other game types.

## Workspace and responsive sizing

The game workspace should behave as one proportional composition rather than a collection of independently stretched controls.

### Reference sizing

- Periodic-table placeholders are the reference unit.
- Table cells stay square at every supported size.
- Loose draggable element tiles are **90% of the table-cell width and height**.
- Element tiles retain their own aspect ratio and remain visually smaller than their destination placeholders.
- Text, gaps, legend items, controls, and surrounding UI scale consistently with the workspace rather than stretching non-uniformly.

### Filling the browser window

The table and element pool should use as much available viewport space as practical while preserving proportions.

On a wide desktop:

- periodic table remains docked on the left/main side;
- element pool remains docked on the right;
- the existing splitter may continue to allocate relative space between them;
- changing the splitter must not distort table cells or element tiles.

The layout should choose the element-pool column count from the available area. Small sets should naturally form compact trays; larger sets should use more columns and rows.

The layout should prefer fitting the selected element pool without scrolling by making efficient use of the available area. It must not shrink below a legible minimum merely to force every element on screen. If the viewport cannot accommodate the pool while preserving the 90% tile relationship and minimum readability, the element panel may scroll as a fallback.

### Narrow screens

When the browser is too narrow for a useful side-by-side layout, the composition should switch as a whole rather than progressively squash the table and pool.

The preferred narrow layout is:

1. periodic table
2. element pool below it

Both retain the same proportional sizing rules.

### Resize behaviour

Resizing the browser should feel like zooming/reflowing the complete application:

- table cells remain square;
- element tiles remain at the 90% relationship;
- panels reflow at defined breakpoints;
- unused width/height is redistributed through layout space, rows, columns, and panel allocation rather than by distorting components.

If the splitter position is user-adjustable, remember its desktop allocation locally so the user does not have to set it again each game. A stored splitter preference must not prevent responsive fallback on narrower windows.

## Existing behaviour to preserve

v21.7 must not change the established game rules:

### Single Player

- draggable elements
- movable placed tiles and replacement behaviour
- category colouring
- sort modes
- independent table/element colours
- atomic-number toggle
- tooltips
- Beginner / Intermediate / Advanced / Custom settings
- Check Answers
- Hint
- Show Answers
- Reset
- Print
- legend and help-bar options

### Local 2 Player

- two players
- correct answer locks the placement, scores, increments streak, and keeps the turn
- wrong answer scores zero, resets streak, returns the tile, and changes turn
- existing streak scoring
- selected element-set completion

### Online 2 Player

- anonymous authentication
- room codes and invite links
- trusted `/answers` validation
- trusted `/elementSets` validation
- presence and reconnect grace
- expiry/cleanup behaviour
- host-selected settings
- rematch support
- category membership validation
- existing v21.5/v21.6 compatibility where currently supported

## Firebase scope

No new Firebase data model is intended for v21.7.

The Online create flow should continue to write the existing v21.6 room schema for the sole v21.7 game type. The Join Game redesign should continue to consume that schema.

If implementation reveals that a schema or rule change is unavoidable, work must stop and the design must be revised before changing production Firebase rules.

## Error handling

- Invalid or unavailable element sets prevent game start and show a clear setup error.
- Online Create Room errors remain visible in the New Game dialog/status rather than silently closing it.
- Join errors remain visible in the Join Game dialog/status.
- Cancelling either dialog has no gameplay side effects.
- A guest joining an unsupported room version receives the existing compatibility error rather than entering a partially configured game.

## Testing

Implementation will use test-first development.

Automated coverage should include at minimum:

- Play mode dropdown is absent and New Game / Join Game controls exist.
- All New Game element choices come from `PeriodicElementSets`.
- Single Player resolves First 20, First 36, All 118, and category sets correctly.
- Single-player completion and reset use selected-set counts.
- Out-of-set table positions are inactive in Single Player.
- Existing Local and Online element-set behaviour still works.
- New Game mode switching does not mutate an active game until confirmation.
- Join Game does not expose editable host settings.
- Invite-link room codes feed the Join Game path.
- Table placeholders remain square and element tiles preserve the 90% sizing contract at representative viewport sizes.
- Responsive layout switches from side-by-side to stacked without changing the tile/table ratio.
- Existing v21.6 category, UI-contract, and Firebase-rules tests remain green.

Before promotion, perform manual browser checks for:

- Single Player: First 20, All 118, Noble gases, and one f-block set.
- Local 2 Player: create, correct/wrong turns, finish.
- Online: create, join from a second device, correct/wrong turns, finish, rematch, leave/reconnect.
- Desktop resize across wide and narrow windows.
- A small category set and All 118 element-pool layout.

## Release and rollback

Development occurs on `v21.7-new-game`, based on `v21.6-known-good`.

`v21.6-known-good` remains untouched as the rollback checkpoint until v21.7 passes automated and live acceptance testing.

The live `v21.2-online` branch must not be moved to v21.7 until the new setup flow, Single Player sets, Local 2 Player, and Online 2 Player have all passed acceptance testing.

## Explicitly deferred

The architecture should leave room for these, but v21.7 does not implement them:

- timed mode
- configurable time limits
- weak-elements practice
- custom hand-picked element sets
- names-to-symbols quizzes
- symbols-to-names quizzes
- atomic-number quizzes
- additional scoring systems
- player accounts or cloud progress history
